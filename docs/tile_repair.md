# 损坏瓦片修复

已有瓦片损坏时，怎样只重下坏的部分，并确认修复完成？

## 操作

1. 填入天地图 Token，在「检查 MBTiles」窗口选择原下载任务的输出文件。
2. 点击「校验并修复」。已标记完成的任务也可以重新校验；下载后发现损坏时，失败提示也提供此入口。
3. 等待校验、下载和修复后全量复检结束。主窗口显示进度，可取消。

普通「继续」为快速续传，只查坐标存在性；「深度检查」只读文件，不修改瓦片。
「校验并修复」会逐张读取已有图片并完整解码，保留健康瓦片，仅下载损坏与缺失坐标。
该操作增加本地 IO 和 CPU 开销，但健康瓦片不消耗 HTTP 请求。

## 完成判据

修复复用原任务的图层、注记、范围、Zoom 和区域边界，并先检查 MBTiles 元数据兼容性。
校验采用 PNG/JPEG 文件头、容器校验及实际像素解码；可识别文件头正确的坏图、截断 JPEG，
以及 CRC 正确但压缩流损坏的 PNG。修复要求安装 Pillow，缺依赖时直接停止，不把所有图片误判成坏图。

新下载内容也必须完整解码后才能写入，坏响应不会覆盖原数据。结束后落盘并全量扫描整个库。
结果分别报告发现的损坏数、成功修复数、发现但未修复数及复检结果。
只有下载无失败、目标瓦片齐全、校验有效且全量复检完成，才能标记为「已完成」。

取消会保留已写入的数据；未结束的复检不代表通过。再次点击「校验并修复」会重新校验，
只请求剩余损坏或缺失部分。普通续传仍保持快速模式，不替代再次修复。

## 边界与失败恢复

- 需要原下载任务记录和 Token，不从未知文件推断来源或下载范围。结构损坏、元数据不兼容或缺少区域边界时应先解决这些问题。
- 仅修复原任务定义内的坐标，不为范围外的多余数据扩大下载。全库复检仍发现损坏时会保持失败。
- 源站继续返回坏图或请求失败时，本轮失败，保留原数据和已完成的修复，网络恢复后再次修复。
- 单任务、修复与计划下载共用运行闸门；计划暂停但线程仍在时也不能并发修复。
- 地图包是独立副本：修复原文件后需重新打包、校验摘要并传输；不直接修改已发布包以免摘要失效。
- 覆盖传输保留旧包，需额外空间容纳新包。新包暂存校验成功后才备份、替换旧包；恢复失败时会报告保留的备份路径。

## 自动验收

先安装 `requirements.txt` 与 `requirements-dev.txt`，在项目根目录运行：

```powershell
.venv\Scripts\python.exe scripts/verify_repair.py
.venv\Scripts\python.exe scripts/verify_stability.py
```

`verify_repair.py` 不触网：用 Mock HTTP 与真实 SQLite 验证损坏诊断、普通续传、只重下坏瓦片、
完整复检、重复修复零请求、坏源失败及再次修复。`--keep` 可保留独立临时产物。

`verify_stability.py` 汇总传输故障、任务互斥、估算后台化、修复服务与界面接线回归，
并运行普通下载打包、分级链路与文档检查；任一阶段失败即非零退出。
历史 GUI 验收脚本已改为等待后台估算结束，不用固定空转次数推测线程完成。
当前推荐区间为全国 Z5~10、省 Z9~13、市 Z12~15、县 Z14~17、任务区 Z15~18。

Android 真机断线、空间不足及回滚验收另见[端到端验收清单 F 段](e2e_acceptance_checklist.md)。
模拟设备检查不能替代真机验收。
