# Windows 侧

## 1. Token 无效 / 天地图返回错误

**症状**：下载一开始就全部失败；连通性测试报错；日志里出现 `403` / `401` /
"Token 无效"。

**确认**：

```bash
cd D:/project/MapDownloader && .venv/Scripts/python.exe -m app.main
```

打开「连接检查」面板点一次测试。

**常见原因与修法**：

| 日志里的关键字 | 原因 | 修法 |
| --- | --- | --- |
| `401` / `403` / 返回体里有 `TOKEN` | Token 错、过期、或没填 | 到天地图官网重新申请，填进「偏好设置」 |
| `域名不匹配` / `referer` | 申请的 Token 绑了域名 | 申请时选"浏览器端"或"服务端"要与你填的一致 |
| `配额` / `超出` / `日均` | 当日调用量用完了 | 换 Token，或等次日 |
| `SSL` / `certificate` | 企业网络做了中间人代理 | 见本表下一行 |

**企业网络 / 代理**：本工具走系统代理。若公司网络需要证书，报错会是一长串
`SSLError`。这类问题**不是工具能修的**，需要 IT 加白或让你走直连。

> ⚠️ **日志里不会出现完整 Token。** 工具刻意压掉了 httpx 的请求日志
> （那里会带上 `tk=<你的Token>`）。所以别指望从日志里"看到 Token 对不对" ——
> 用「连接检查」面板。

## 2. 下载失败 / 一直卡在 0%

**症状**：进度条不动；已下载数不涨；任务状态是"失败"。

**确认顺序**：

1. **先看是不是 Token 问题** —— 见上一条。0% 且立刻失败，八成是它。
2. **看是否网络受限**：能不能打开 `https://www.tianditu.gov.cn/`。
3. **看输出目录**：启动时的环境检查会报。若日志里是
   `[✗] 输出目录：...(影响：无法保存下载的瓦片与地图包)`，先解决它。

**"下载到一半失败"是正常的** —— 网络抖动、对方限流都会让个别瓦片失败。
处理方式：

- **重跑同一个任务**：支持断点续传，已下好的瓦片不会重下。
- 全量重下**不需要**，除非你想换层级或范围。

**HTTP 429 限流**：默认 3 个瓦片 worker、合计 4 HTTP 请求/秒。底图、注记和
所有重试共用一个限速器；合成模式每张瓦片需两个图层请求，日志中的「尝试 6 次」
可能是两层各 3 次的累计数。

收到 429 后，所有等待中的图层与重试一起冷却，速率减半（最低 0.5 请求/秒）。
没有有效 `Retry-After` 时按 5、10、20、40、60 秒退避并添加少量正向抖动；
有该响应头时支持秒数和 HTTP 日期，等待时间不会短于服务端要求，即使超过 60 秒。
相同冷却代次已经在途的多个 429 合并处理，不因同时返回而反复减速。
稳定至少 15 秒且累计 20 次有效响应后，每个恢复窗口提速 25%，最高回到配置上限。

持续限流达到保护阈值（默认 5 个未恢复的限流事件）时，本轮下载会停止，保留已经
写入的瓦片，剩余瓦片如实显示为「未处理」，任务可稍后继续。不会显示成用户取消
或已完成；计划会停在失败条目，不会继续请求下一条。冷却期间也可以暂停或取消。
如果稍后仍被限流，检查 Token 配额和使用同一账号的其他程序；默认速率是本工具的
保守值，服务端限额仍以账号实际配置为准。不要连续重启或同时启动多个下载程序。

离线验收：`python scripts/verify_stability.py`，其中的 `tests/test_adaptive_download.py`
使用 MockTransport 验证冷却、限流保护、暂停取消及续传，不向真实服务发送测试流量。

## 3. MBTiles 检查报"缺瓦片"

**症状**：检查结论是 WARNING 或 FAIL，提示某些级别的某些行列缺失。

**先判断这是不是问题**：

- **少量缺失 + WARNING**：正常。天地图在某些区域本身就没有瓦片（海域、境外的
  一部分），工具会把它算作"范围内应有但拿不到"，提示你注意。
- **大比例缺失 + FAIL**：不正常，说明下载真的失败了。回到上一条重跑。

**确认缺在哪一级**：检查报告里会按级别列出覆盖率。若只有最深一级缺得多，
通常是下载被中断在最后。

**这不是包坏了**：MBTiles 结构完整、其他级别的瓦片都在，地图照样能用，
只是放大到最深一级时会看到空块。

## 4. 地图上下颠倒 / 位置偏移

**这是整套流程里最"经典"的一类问题**，且症状很有辨识度：地图能显示、
瓦片数量也对，但**南北颠倒**（或者偏了整整一半）。

**根因**：XYZ 与 TMS 的行号方向不同。

| 场景 | 用的方案 |
| --- | --- |
| 工具 / API / Package 协议 | **XYZ**（原点在左上） |
| MBTiles 内部的 `tile_row` | **TMS**（原点在左下） |

翻转只在**两处**发生：写 MBTiles 时（`MbTilesWriter`）、读 MBTiles 时
（osmdroid 的 Provider）。**协议里没有行列号字段**，所以这个问题不可能
出在 `manifest.json` 上。

**怎么确认是这一类**：

```bash
# 在 Windows 上，看某个已知位置对应的瓦片在库里的 row
cd D:/project/MapDownloader && .venv/Scripts/python.exe -c "
from app.geo.tile_math import lat_to_tile_y, xyz_y_to_tms_y
z, lat = 12, 39.9
xyz = lat_to_tile_y(lat, z)
print('XYZ y =', xyz, ' TMS row =', xyz_y_to_tms_y(z, xyz))
"
```

然后到 Android 侧的 MBTiles 里查这一行在不在（`troubleshooting` 的这一节由
Android 侧负责执行）。**若库里存在的是 `xyz` 那一行而不是 `tms` 那一行，
说明写入端少翻了一次。**

**若你是开发者**：这类 bug 单测抓不到 —— "能写、能读、数量对"三条全成立。
唯一可靠的守护是**已知坐标往返**用例（`tests/test_mbtiles_writer.py` 里有）。

## 5. Package 校验 SHA256 失败

**症状**：生成地图包时报"自校验未通过"；或校验一个已有包时报 SHA256 不一致。

**逐条确认**：

| 检查 | 命令 |
| --- | --- |
| 文件是否完整 | `dir map.mbtiles`（看字节数） |
| manifest 声称的大小 | 打开 `manifest.json` 看 `mbtiles.size` |
| 实际哈希 | `(Get-FileHash map.mbtiles -Algorithm SHA256).Hash.ToLower()` |

**三种可能**：

1. **两个值都对不上** → 文件被改过 / 传输截断了。
2. **`size` 对得上但 `sha256` 对不上** → 文件在**同样长度**下被改过（少见），
   或者哈希算法/编码不对。manifest 里必须是 **64 位小写十六进制**。
3. **`size` 就对不上** → 文件被截断。重新生成或重新传输。

**边界情形**：如果你手动改过 manifest（比如把 `description` 改了个字），
**不会**影响 SHA256 —— 那个哈希只覆盖 `map.mbtiles`，不覆盖 manifest 本身。

# 传输

## 6. 工具里找不到 ADB / 设备列表为空

**先确认一件事**：ADB 只影响"从工具里直接传到设备"。
**它不影响你做地图。** 没 ADB 就用 U 盘 / 网盘 / `adb` 命令行自己推。

**确认**：

```bash
D:/develop/android/sdk/platform-tools/adb.exe version
```

**修法（按优先级）**：

1. 工具「偏好设置」里显式填 adb 的**绝对路径**，例如
   `D:/develop/android/sdk/platform-tools/adb.exe`
2. 设环境变量 `ADB_PATH` 指向它。
3. 把 `platform-tools` 加进系统 `PATH`。

**注意**：工具启动时的环境检查里，ADB 那一项标的是 `[!]` 而不是 `[✗]` ——
这不是笔误，是刻意的分级（见 `e2e_acceptance_checklist.md` 的 A2）。

**设备列表为空但 `adb version` 正常**：

- 手机没开 USB 调试（在「开发者选项」里）。
- 数据线只供电不传数据（换一根线试试）。
- 用无线调试时要先 `adb connect <ip>:<port>`。

## 7. 设备显示 unauthorized / offline

| 状态 | 含义 | 修法 |
| --- | --- | --- |
| `unauthorized` | 手机上没确认过这台电脑 | **看手机屏幕**，点「允许 USB 调试」。若没弹窗，撤销授权后重新插 |
| `offline` | 连接僵死（常见于拔插、休眠唤醒后） | `adb kill-server` → `adb start-server` |
| `no permissions` | Linux 下 udev 规则问题 | 配 udev 规则（Windows 上少见） |

**这类状态会让传输直接失败，且报错文本可能很含糊**。修好之后再重试传输，
不需要重新生成地图包。

---

## 8. 传输中断 / 设备空间不足

**空间不足**：

工具会在传输前检查设备剩余空间，并在偏紧时警告。需要多少？
**至少要包大小的 1 倍**（传输是直接写文件），但如果设备上已有同名包、
并且你选了覆盖，实际需要更多（旧包 + 新包在切换的一瞬间同时存在）。

**确认设备剩余空间**：

```bash
D:/develop/android/sdk/platform-tools/adb.exe -s <serial> shell df -h /sdcard
```

**传输中断**：

- 重新推一次，覆盖即可（`adb push` 是逐字节写，中断会留下半个文件）。
- 推完之后**必须核对字节数**：
  ```bash
  D:/develop/android/sdk/platform-tools/adb.exe -s <serial> shell ls -l /sdcard/Download/<包名>/map.mbtiles
  ```
  与 Windows 上的值不一致 → 说明没传完，别急着导入。

> `adb push` 的进度写在 **stderr** 上。用脚本抓输出时只读 stdout 会得到空串，
> 看起来像"什么都没发生"。

# Android 侧

## 9. 导入失败

界面会给出**不带错误码**的中文说明（错误码只在日志里）。按提示分类：

| 界面提示 | 含义 | 怎么办 |
| --- | --- | --- |
| 包内缺少 manifest.json | 选错目录了 | 选到**包含** `manifest.json` 的那一层 |
| manifest.json 非法 | 文件坏了 / 被改过 | 回 Windows 重新生成 |
| **该地图包版本过高，请升级应用** | `formatVersion > 1` | 升级 App，或让 Windows 侧用旧格式生成 |
| 包标识非法 | `id` 里有非法字符 | 重新生成（正常生成的包不会有这个问题） |
| 包内缺少 manifest 声明的 MBTiles 文件 | `map.mbtiles` 没传过来 | 回传输步骤补 |
| **MBTiles 实际大小与 manifest 声明不一致** | 传输截断了 | 重推 |
| **MBTiles 的 SHA256 与 manifest 声明不一致** | 文件内容不对 | 重推；仍失败则重新生成包 |
| MBTiles 结构校验未通过 | 不是有效的 SQLite / 缺表 / zoom 与 manifest 冲突 | 重新生成包 |
| 设备存储空间不足 | 见下 | 清理空间 |
| 复制地图文件失败 | IO 错误（源被拔出 / 权限被收回） | 重试 |
| 安装到正式目录失败 | 搬运/回滚失败 | 看日志详情 |
| 同名离线地图已存在 | 需要你确认是否替换 | 确认后重试 |

**"空间不足"要多少**：包大小的**两倍以上**。导入会先写到临时目录
（`.importing`），校验通过才搬到正式位置 —— 切换的那一瞬间两份同时存在。

**导入中断了怎么办**：App 下次启动会清理 `.importing` 残留。
也可以在管理页手动触发清理。**中断不会留下半个"能用"的包** ——
正式目录里只会在校验通过后才出现东西。

## 10. 导入后列表里显示"已损坏"

**症状**：包出现在列表里，但标着"已损坏"或给了原因。

**这是刻意设计的**：管理页在装配列表时会**真的打开一次** `map.mbtiles`
读一张瓦片。能导入但读不出瓦片，多半是这两个原因：

| 原因 | 确认方式 |
| --- | --- |
| 文件头不是 `SQLite format 3` | 传输坏了 → 重推并核对 SHA256 |
| `tiles` 表为空，或 zoom 区间与 manifest 冲突 | 包本身有问题 → 重新生成 |

**为什么不做"装作看不见"**：如果这里放过，用户会一路点到"使用"，
然后得到一张空白地图 —— 而且不知道该怪谁。宁可在列表里就说清楚。

**"已损坏"的包不会被删掉**：它还在设备上，你可以自己检查或删掉。
工具**不会**自动删除用户的文件。

## 11. 切到离线后地图黑屏 / 空白

这是最需要系统排查的一类。**按顺序**查：

### ① 模式真的切成 OFFLINE 了吗

看模式选择器显示的是不是 `OFFLINE`。若是 `AUTO`，它可能因为当前位置
不在这张包的范围内而**没选中任何包**（这是正确行为，见 §13）。

### ② 包的 zoom 区间覆盖当前缩放吗

如果你当前在地图页缩放到 16 级，而包只有 11~13 级，**超出部分必然空白**。

**确认**：看列表行摘要里的 zoom 区间，或看 `manifest.json` 的
`minZoom` / `maxZoom`。

**修法**：在 Windows 侧重新下一个包含你需要的层级的包。

### ③ 当前视野在包的 bounds 里吗

在包范围外看，同样是空白。

**确认**：在管理页的行摘要里能看到包的覆盖范围。

### ④ 是不是"已损坏"的包

见上一条。列表里有标记。

### ⑤ 都正常但还是空白

**看日志**。App 会把离线加载的失败原因写进日志（含 Provider 装载、
瓦片读取失败）。若日志里出现"文件被占用"之类，试试切到别的页面再回来 ——
有时是文件句柄没释放。

**若仍查不出**：改用**联网 + ONLINE** 确认在线底图是好的。若在线也空白，
问题不在离线这条链路上（可能是网络或 Provider 配置），与本工具无关。

## 12. 缩放层级不对（放大到最大就白）

**症状**：地图能看，但放大过某个级别就什么都没有。

**这不是 bug，是包的覆盖范围。** 离线包只包含你下载的那些层级。

**确认**：

```bash
# 看包声称的区间
cat <包目录>/manifest.json | grep -E "minZoom|maxZoom"
```

**注意区分两种区间**：

| 区间 | 来源 | 含义 |
| --- | --- | --- |
| manifest 的 `minZoom`/`maxZoom` | 你下载时选的 | **包里有这些层级的瓦片** |
| 地图页能缩放到多少 | osmdroid 的设置 | 你能操作到多少级 |

放大到 manifest 的 `maxZoom` 以上，地图会**保持显示最后一层的瓦片**
（放大但不重采样），而不是变白 —— 若你看到的是**变白**，
说明连 `maxZoom` 那层都没读到，回到上一条排查。

---

## 13. AUTO 模式没选中离线地图

**先确认这可能是正确行为。** AUTO 的规则是：

1. 当前位置（或地图中心）**在包的 bounds 内** → 才可能选中；
2. 多张包都覆盖时，**框小的优先**（更精确的那张）；
3. 同样大小时，**maxZoom 高的**优先；
4. 再相同，**更新时间新的**优先；
5. **一张都匹配不上 → 安全退回在线底图**（不是保持上一张、也不是白屏）。

**所以"没选中"最常见的原因是：你不在任何包的范围内。**

**确认**：

- 地图页当前中心点，落在列表里某张包的范围内吗？
- 若在范围边缘，可能只是差一点点（有 1e-4 度左右的容差）。

**若位置确实在范围内却仍没选**：

- 该包在列表里是不是"已损坏"？损坏的包不参与 AUTO。
- 是不是**断网**？断网 + AUTO **有**覆盖包时应该选离线包；
  断网 + 无覆盖包时保持在线（但显示不出瓦片，这是正常的，因为断网了）。

**若你希望"始终用某一张包"**：不要用 AUTO，直接切 `OFFLINE` 并指定那一张。

## 14. 切不回在线 / 在线一直转圈

**首先区分两件事**：

| 现象 | 含义 |
| --- | --- |
| 切到 ONLINE 后**底图出来了，但很慢/有空白块** | 网络慢，**不是 bug** |
| 切到 ONLINE 后**完全不显示，一直转圈** | 网络不可用，或在线图源有问题 |

**确认网络**：切到 ONLINE 之前，设备真的联网了吗？飞行模式开着的话，
在线底图**必然**出不来 —— 这时候应该用 OFFLINE。

**"切不回在线"的另一种含义**：模式显示 ONLINE 了，但底图还是离线那张。
这种情况请确认：

- 列表里那张包的「当前使用」标记是否消失了？
- 地图页是否刷了一下？

**若卡住**：切到 OFFLINE 再切回 ONLINE（走一次完整的切换）。
仍然不行就重启 App —— 那说明有状态没清干净，值得记下来反馈。

## 16. 续传说"找不到区域边界，无法安全续传"

**症状**：任务列表里一条"已暂停"的任务点续传，报：

> 任务记录的区域（region_id='xxx'）在本版本找不到对应的行政区边界，无法安全续传

**为什么它宁可停下也不退回矩形**：任务记录里只存了 `region_id`（不存几 MB 的 GeoJSON）。
恢复时按 `region_id` 去区域目录里查几何，按那份几何算"还缺哪些瓦片"。
查不到就用外包矩形继续下的话，会**多下**区域外的瓦片（也可能因为判据不同而少下）——
用户看到的是"续传完了但地图边角多出一圈"，比停下来难查得多。

**怎么确认是哪一种**：

| 情况 | 怎么判断 | 怎么办 |
| --- | --- | --- |
| 边界文件被删了 / 没放进 `resources/regions/` | 工具的「区域」下拉里那块地还在吗 | 把 GeoJSON 放回去再续传 |
| 任务记录里那块地**本来就不在**目录里（老记录、别人的数据） | 下拉里根本没有这个 id | 重新建任务（原记录可以删掉） |
| 目录里有这块地，但还是报这个错 | 检查 `index.json` 的 `id` 与记录里的 `region_id` 是否一致 | 是 bug，把两边的 id 记下来反馈 |

**任务区不受影响**：它的几何存在用户数据目录（`mission_regions/`），
跟着任务记录走，不存在"反查不到"的问题。

## 17. 计划里逐项串行，看起来像卡住

**症状**：下载计划点了开始，第一项在下载，其它项全写着"待下载"，
一动不动十几分钟。

**这是设计如此**：计划**严格串行**，一项都没跑完不会开第二项。

**为什么不做并发**：日志与进度会交错，`Inspector` 的阶段性结论没法归属到某一项，
而且并发下载对天地图的配额与本地磁盘 IO 都不友好 —— 一个瓦片服务端限速，
并发不会更快，只会让"哪一项失败了"变得含糊。

**怎么确认它真的在动**：

```bash
# MBTiles 文件在长大（不一定每秒钟都长，看 size 的变化趋势）
ls -l <输出目录>/*.mbtiles
```

界面上那一行的进度与右侧的日志区都会滚动。**完全没有新日志**才需要担心。

**真的卡住了怎么办**：点「暂停」再点「继续」—— 任务级续传会重算"还缺哪些"，
把卡住的根源（多半是网络请求超时）绕过去。连续两次都在同一个进度停住，
那就是那块瓦片有问题，看 `troubleshooting.md` 第 2 条。

## 18. 风险提示说"危险"，但我就想下自己那块

**这是提醒，不是限制。** 风险提示全部是"拦一下、让你确认"，没有任何一条会
阻止你下载。

| 档位 | 界面表现 |
| --- | --- |
| NORMAL | 不打扰 |
| LARGE / VERY_LARGE | 弹确认框，点「是」继续 |
| DANGEROUS | 弹确认框，**要手输确认词**才放行 |

**为什么 DANGEROUS 要输确认词**：那是十亿张瓦片 / 100 GiB 量级，
多半是"Zoom 填错了"而不是"真的要下这么多"。确认词的成本是几秒钟，
误点一次的成本是几天的带宽与配额。

**如果你确实要下**：确认框里会说明是哪一维触发的（张数还是容量）。
点「查看详情」能看到**逐 Zoom 的张数与容量**，据此可以把上界砍掉一两级 ——
通常砍掉 Zoom 上界最后两级，张数会降到原来的几分之一。

**"我只是选了个小范围也报危险"**：看详情里的实际 Zoom 区间。
小范围 + 高 Zoom 完全可能危险（1 km 的走廊下到 Z18 也是天量）。
真正无关的是"等级"本身 —— **高 Zoom 不是危险信号，规模才是**。

## 19. 升级后"我上次选的县不见了"

**现象**：上一版选到某个县（区），关掉再开（或从旧版本升级上来），
县区下拉回到「全部」，范围变成整个市或整个省。

**两段历史原因，都已在 Slice 28 修掉**：

1. **偏好里根本没存县**（旧版本）。`RegionSelection` 只有
   `country/province/city` 三段 id，所以关窗时县被丢掉 —— 旧版本存的配置里
   **本来就没有** `download/county_id` 这个键，升级后自然恢复不出来。
   重新选一次县、关一次窗，之后就能正常记住了。
2. **直辖市下辖区 / 省直辖县级市选不上**（旧版本的代码缺陷）。
   这类县的父级是**省**、中间没有市，而"城市"下拉在"省下没有市"的分支里
   会顺手把刚选好的县清掉 —— 表现是 `set_region_id()` / 双击任务回填 /
   恢复偏好时，界面停在"重庆市"而不是"渝中区"，且**不报错**。
   真实目录里这类县有 155 个（重庆 37 个下辖区 + 各省直辖县级市）。

**怎么确认当前版本有没有这个问题**（一条命令）：

```bash
cd D:/project/MapDownloader
.venv/Scripts/python.exe -m pytest -q tests/test_download_panel_region_selection.py -k county
```

8 条全过就没事。**手工复验**：区域选「重庆市」→ 城市下拉应显示
「暂无城市数据」→ 县区下拉里选「渝中区」→ 关窗重开 → 应仍是渝中区。

**升级后要做什么**：不需要迁移。旧配置没有县 id，恢复流程会按
**县 → 市 → 省 → 国** 逐级回退，落在市（或省）上并写一条 WARNING 日志 ——
不会静默，也不会把整条选择链扔掉。

## 附：这些情况不是 bug

避免浪费你的时间，列出几个"看起来像问题其实是设计如此"的：

| 现象 | 为什么是设计如此 |
| --- | --- |
| ADB 那一项显示 `[!]` 而不是 `[✗]` | ADB 只影响设备传输，不影响做地图 |
| 环境检查结论写"1 项功能不可用：ADB" | 同上，这是刻意分级 |
| AUTO 模式下从北京飞到上海后底图变了 | 没有包覆盖上海，正确行为是退回在线 |
| 导入一个包后列表里多了一行"已损坏" | 那是**另一个**坏目录，不是你刚导入的 |
| 删包时有确认框 | 删掉的是用户的文件，必须二次确认 |
| manifest 里没有 `description` | 它是唯一的可选字段，为空时**不写这个键** |
| 地图放大到 `maxZoom` 以上不再变清晰 | 包只含到 `maxZoom`，这是"无更多数据" |
| `.importing` 目录存在 | 上次导入中断的残留，下次启动会清理 |
| 计划里各项逐项串行、后面的写着"待下载" | 调度是**严格串行**的设计（见第 17 条） |
| 小范围 + Z18 也弹"危险"确认框 | 张数/容量是唯一判据，与范围大小和等级无关（见第 18 条） |
| 推荐区间是 Z5~10，界面允许我填 Z18 | 推荐只提示、不限制（见第 18 条） |
| 行政区包重新打一次才带上 `level` | 老包不会自动补元数据（见第 15 条） |


## 损坏瓦片续传后仍无法显示

普通「继续」只检查坐标存在，不解码全部已有图片。请在 MBTiles 检查窗口选择原任务
输出文件，点击「校验并修复」；该操作需要原任务记录与 Token，可修复已标记完成的任务。
它保留健康瓦片，仅重下损坏与缺失部分，并以全量复检结束。

若网络继续返回坏图，修复会失败而保留原数据；再次点击修复可重试。
找不到原任务时不会自动推断来源，尤其不要直接修改已打包的副本。
详见[修复操作与验收](tile_repair.md)。


## 下载目录有地图，但「选择地图包」找不到

下载结果是 `.mbtiles` 文件；成品地图包是包含 `map.mbtiles` 与 `manifest.json` 的目录。
旧版入口只允许选择目录，因此不会显示下载的文件。

新版点击「选择地图包」，可直接在 `output` 选择 `.mbtiles`。程序自动打开生成地图包
窗口并在后台检查地图；确认名称、输出位置后点击「生成地图包」。生成成功后自动选中
成品包并在后台校验，接着可传输到设备。检查失败时先检查、补齐或修复源地图。
已有成品包可选择其中的 `manifest.json` 或 `map.mbtiles`，也可点击「选择包目录」。
下载或修复进行中时，请先完成或暂停再从此入口打包；生成过程不会修改源 `.mbtiles`。
更新代码后需关闭旧程序并重新启动，使选择入口生效。
