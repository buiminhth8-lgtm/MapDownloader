# 下载风险分析（Slice 23）

一句话：**在按下「开始下载」之前，把"这一单有多大、要不要拦一下"算清楚、说明白。**

这一版加的不是"另一个确认框"，而是一层**结论**：它有等级、有原因、有建议、有明细，
并且是界面上**所有**确认动作的唯一判据来源。用户看到的等级、日志里记的等级、
拦住他的那个框里的等级，必然是同一个字符串。

---

## 1. 它解决的问题

在这之前，"这一单大不大"只体现为一个 1 万张的阈值（Slice 4 的
`GUI_LARGE_TASK_CONFIRM_TILES`）：超过就问一句"确定吗"。三个问题：

1. **把三件不同的事当成了一件。** "一个大地级市的 Z4~10"（几十万张、几百 MB）
   与"全国 Z8~18"（上亿张、几十 TB）在同一个阈值眼里都是"大任务"，问的是同一句话。
   前者是正常作业，后者会下到下个月。
2. **只按张数判，看不见磁盘。** 全国 Z4~10 张数不算多，但没有任何一份
   "这次要写多少字节"的结论摆在用户面前 —— 而把磁盘写满是这个工具最贵的失败方式
   （不可逆、且发生在几小时之后）。
3. **拦下来也说不清为什么。** 一个 Yes/No 框里只有"预计 189,342 张"，
   用户没法判断"这算多吗"，于是学会了闭眼点右边那个。

Slice 23 把这件事拆成：**一张阈值表**（策略层）+ **一份报告**（纯计算层）
+ **三处展示 / 拦截**（界面层）。三者之间只有数据流，没有判断重复。

---

## 2. 四个等级与两张阈值

```
NORMAL       < 100 K 张   且   < 2 GiB      直接开始
LARGE        100 K ~ 1 M      2 ~ 20 GiB    开始前确认一次（问号图标）
VERY_LARGE   1 M ~ 10 M       20 ~ 100 GiB  明确警告后确认（警告图标）
DANGEROUS    ≥ 10 M           ≥ 100 GiB     手输确认词才放行
```

阈值定义在 `app/planning/risk_policy.py` 的 `RiskPolicy`（`DEFAULT_RISK_POLICY`
是**全项目唯一一份**）。界面、对话框、验收脚本一律只允许**问**它：

```python
policy.level_for(tiles, size_bytes)          # 分档
policy.requires_confirmation(level)          # 这一档要不要弹框
policy.requires_strong_confirmation(level)   # 这一档要不要手输确认词
```

### 为什么两个维度都算、取更高

- **只看张数**：把"全国 Z4~10"（几十万张、每张很小）与"一条走廊 Z18"
  （同样几十万张、但密得多）合并成一档；
- **只看容量**：低估高并发的小瓦片任务（请求数与耗时都是它决定的）。

平均 30 KB/张，所以两张阈值表并不同构（20 GiB ≈ 71.5 万张，而不是 100 万张）
—— 这恰恰是"不能换算一次"的证据。

### 为什么不能"Zoom 高就是危险"

任务区 Z15~18 的 Zoom 数字比全国 Z4~10 高得多，但它只覆盖一条走廊（几万张）。
**等级只参与策略判断**（推荐区间、建议文案），最终风险一律看实际张数与容量。
这条在 `tests/test_risk_policy.py` 里有一条专门的用例守着。

## 3. 数据流

```text
RegionTileEstimate / DownloadPlanItem      ← 已经算好的估算（唯一输入）
    │   selected_tiles / estimated_size_bytes / per_zoom
    ▼
DownloadRiskAnalyzer.analyze()              单块地 → DownloadRiskReport
DownloadRiskAnalyzer.analyze_item()         计划条目 → DownloadRiskReport
DownloadRiskAnalyzer.analyze_plan()         整份计划 → PlanRiskReport
    │   阈值来自 RiskPolicy，推荐区间来自 ZoomStrategyService
    ▼
报告自己产出全部展示文本（tiles_text / size_text / headline_lines / as_lines）
    │
    ├─ 面板「风险提示」区（DownloadPanel.set_risk_report）
    ├─ 「查看详情」窗口（RiskDetailsDialog，逐 Zoom 四列表）
    ├─ 单任务启动保护（MainWindow：LARGE 问号 / VERY_LARGE 警告 / DANGEROUS 强确认）
    └─ 计划表格「风险」列 + 合计 + 「开始计划」四选一 / 强确认
```

三条硬约束（都有用例或 AST 守着）：

1. **只吃现成的估算结果，绝不重新枚举瓦片。** `DownloadRiskAnalyzer` 里没有任何
   `calculate_tile_range` / `iter_selected_tiles` / `RegionTileEstimator`，
   连 `import` 都没有 —— 它读取估算对象的那三个字段（鸭子类型），
   于是"风险分析的复杂度与区域多大无关"这件事是**结构上**成立的，不是靠自觉。
2. **只用 `selected` 张数。** 外包矩形候选数在渤海湾、广州湾这类形状上能虚高一个
   数量级，拿它当风险依据会得到"你其实下不了这么多，但我按这么多警告你"。
3. **格式化只有一处。** 所有数字走 `app.geo.tile_math` 的 `format_size` /
   `format_tile_count`，因此"面板写 2.74 B、弹窗写 2735435470"这种事不会发生。

## 4. 单任务：面板 + 详情 + 启动保护

### 面板上的「风险提示」区

「计算」跑完之后出现（没算之前整块是**隐藏**的，而不是显示一句"尚未分析"占地方）：

```
┌ 风险提示 ──────────────────────────────────────────────────────────┐
│ 风险：较大（LARGE） ▲                                               │
│ 预计瓦片：100,000                                                  │
│ 预计容量：2.86 GB                                                  │
│ 实际 Zoom：Z9~18      推荐 Zoom：Z9~13                             │
│                    [查看详情] [采用推荐 Zoom]                       │
└────────────────────────────────────────────────────────────────────┘
```

- 等级行直接取报告的 `level_line`（**带机器可读名**：`风险：较大（LARGE）`），
  日志与验收脚本 grep 的是同一个字符串；
- 「高于推荐 Zoom 的瓦片：98.4%」只在真的有超出时出现（恒为 0 的那一行
  只会让人去找"是不是出事了"）；
- **记号不只用颜色**（`✓` / `▲` / `▲▲` / `✕`）：黑白打印、色觉差异都还分得开。

### 「查看详情」

四列表 `Zoom | 选中瓦片 | 预计容量 | 推荐`，数据来自报告的 `per_zoom`
（**复用 estimator 的逐级明细，不重新遍历**）。「推荐」列是三态：

| 取值 | 含义 |
| --- | --- |
| `推荐` | 该 Zoom 不超过推荐上界 |
| `高于推荐` | 超过了（"超推荐张数"就是这些行加起来的） |
| `—` | 自定义等级没有推荐区间，此时**不评价** |

最后那一行是**合计**。表格 `NoEditTriggers`：这是结论视图，能改会让人以为改这里
能改变下载范围。

### 「采用推荐 Zoom」

四条约定：

1. **只有用户点了才会执行**。分析、重绘、启动保护**都不会**调用它 ——
   "我明明填了 Z18"不该变成"它自己变成了 Z10"；
2. 采用的方式是**切到「按推荐值」模式**（`ZoomMode.RECOMMENDED`），
   而不是把两个数硬写进自定义模式：推荐区间会因为"换了一块地"而变，模式跟着走
   才能一直对得上；
3. 改完**立刻重算**（`_run_tile_math`）：否则界面会停在旧的张数上，而它对应的
   已经不是当前 Zoom 了；
4. 自定义区域没有推荐区间 → 按钮**置灰但不隐藏**，并说明"当前无需调整 Zoom"
   （用户该看到"这里本来有个功能，只是现在用不上"）。

### 启动保护（三档）

`MainWindow._continue_plan()` 的顺序：

```
已有文件那一关（Slice 5）过了
  ├─ 报告是 DANGEROUS          → 强确认（手输确认词）
  ├─ 报告是 LARGE / VERY_LARGE → 确认框（问号 / 警告图标，正文 = report.as_lines()）
  └─ 报告是 NORMAL             → 才走旧的 1 万张阈值（GUI_LARGE_TASK_CONFIRM_TILES）
```

**两道闸门不叠加**：新阈值更严（10 万张起），所以两个都命中的任务必然走上面那条，
"一个 20 万张的任务被连问两次"不会发生。
`tests/test_risk_protection_ui.py` 里把旧阈值改小成 1 来验证"只弹一次"。

判据一律来自报告（`requires_confirmation` / `requires_strong_confirmation`），
`_continue_plan` 里**没有任何阈值数字**。

### 危险档的强确认

```
┌ 危险任务强确认 ────────────────────────────────────────────────────┐
│ 风险：危险（DANGEROUS） ✕                                          │
│ 预计瓦片：2.74 B                                                   │
│ 预计容量：76.00 TB                                                 │
│ 实际 Zoom：Z8~18      推荐 Zoom：Z4~10                             │
│ 原因：…                                                           │
│ 建议：…                                                           │
│                                                                    │
│ 这个规模已经进入「危险」档：可能几天都下不完、把磁盘写满、           │
│ 并大量消耗天地图调用配额。                                         │
│                                                                    │
│ 确实要执行的话，请在下面输入 CONTINUE（区分大小写）后点「仍然继续」。│
│ [在这里输入 CONTINUE                      ]                        │
│ 确认词：CONTINUE（区分大小写）                                     │
│                              [取消] [仍然继续]  ← 敲对之前是灰的    │
└────────────────────────────────────────────────────────────────────┘
```

- 确认词来自配置 `DANGEROUS_CONFIRM_WORD`（界面、测试、文档读的是同一个字面量）；
- **大小写敏感**（刻意不做 `upper()`）、忽略首尾空白，全部提示都写在界面上；
- 回车只在确认词正确时才等于"继续"（否则回车会变成绕过闸门的动作）；
- 关窗 / Esc / 点取消一律当作"不继续" —— 默认安全。

## 5. 计划级：风险列 + 合计 + 四选一

### 表格与合计

```
┌ 离线计划 ─────────────────────────────────────────── 输出：D:/out/离线计划 ┐
│ 区域       等级   缩放     预计瓦片    预计容量   状态        风险          │
│ ☑ 示例国   全国级 Z4~10     268 张     7.85 MB   可参与下载  正常 ✓        │
│ ☑ 示例北省 省级   Z9~13   3,449 张   100.98 MB   可参与下载  正常 ✓        │
│ ☑ 示例河市 市级   Z12~16 53,585 张     1.53 GB   可参与下载  较大 ▲        │
│ 合计：3 个区域 / 57,302 张 / 1.63 GB　风险：较大（LARGE） ▲                 │
└────────────────────────────────────────────────────────────────────────────┘
```

（真出现危险项时，合计行还会点名：`（危险任务：示例南省 Z8~18、示例西省 Z9~18）`
—— 等级会被抬到 `DANGEROUS`，但不点名的话用户不知道该停用哪一项。）

三点说明：

- **风险列追加在末尾**（而不是插在中间）：它是前六列的"结论"，
  紧跟在状态后面读起来才是"这一项能不能下 → 下起来有多险"。
  追加在末尾也让前六列的既有下标保持不变 —— 但代码里**不许**再用
  `len(_COLUMNS) - 1` 指代状态列：那样在加了风险列之后，执行符号
  （`✓ 已完成`）会被写进风险列。改用 `_COLUMN_STATUS` / `_COLUMN_RISK`
  两个索引常量，`_COLUMNS.index(...)` 是唯一来源。
- **不可用项显示 `—`**：它连估算都没有（不可用时估算被清空），
  给一个"正常"会是在替一块算不出来的地打包票。
- **停用项不进合计，但那一行照旧显示等级**：停用项不会被下载，把它算进风险
  等于对着一个不会发生的事警告用户；但显示它是有意的 —— 用户停用一块地之后
  往往还要回头看一眼"到底是哪一块那么大"。"不参与合计"与"看不出来有多大"
  是两件事。

计划总等级取**两个来源里更高**的那个：①合计张数 / 容量本身的档位；
②所有参与条目里最高的一档。只做①会漏掉"总量不大但有一项是 TB 级"的计划，
只做②会漏掉"每项都不大、加起来装不下"的计划。

### 计入口径

与 Slice 20 的合计口径**逐字一致**：`counts_toward_total = enabled AND is_valid`。
所以"计划风险"与"合计多少张"永远在说同一批条目。

### 「开始计划」的四选一

`LARGE` 起弹这个窗口；`DANGEROUS` 用的是**同一个窗口**，只是多出一个必须敲对的
确认词输入框：

```
┌ 下载计划风险确认 ──────────────────────────────────────────────────┐
│ 计划合计：57,302 张 / 1.63 GB                                      │
│ 风险：较大（LARGE） ▲                                              │
│ 原因：…                                                           │
│ 建议：…                                                           │
│ 确认开始执行这份计划吗？                                            │
│ [返回修改]              [停用危险项] [采用推荐 Zoom] [仍然继续]      │
└────────────────────────────────────────────────────────────────────┘
```

四个去处的后果：

| 按钮 | 后果 | 本轮是否启动 |
| --- | --- | --- |
| 返回修改（默认） | 什么都不动 | 否 |
| 停用危险项 | 所有危险项停用，合计与风险立刻重算 | 否 |
| 采用推荐 Zoom | 所有超推荐区间的项改回推荐值，**作废估算并立刻重新估算** | 否 |
| 仍然继续 | 按现在的规模跑（危险档要敲对确认词才可点） | 是 |

两个设计取舍：

1. **危险档不叠两个框**（先问"怎么处理"、再问"确认词"）：计划级的两道闸门叠在
   一起会让用户连着回答两个问题，而第二个问题恰恰能被第一个的答案排除掉
   （选了"停用危险项"之后哪里还有危险档要确认）。一次问清。
2. **默认按钮是「返回修改」**，且默认焦点在它身上：误按回车不该把一份危险计划
   跑起来。

刻意**不用** `QMessageBox` 的四个标准按钮：那一屏里要塞一个**输入框**，
而 `QMessageBox` 只能通过 `setCheckBox` 加一个复选，装不下"输入正确才解锁主按钮"
这件事。退出码由 `PlanRiskConfirmDialog` 自己定义
（`RESULT_BACK` / `RESULT_CONTINUE` / `RESULT_APPLY_ZOOM` / `RESULT_DISABLE_DANGEROUS`）。

### 计划层的 `set_zoom`

`PlanService.set_zoom(region_id, min_zoom, max_zoom)`（转发
`DownloadPlanBuilder.set_zoom` → `DownloadPlanItem.set_zoom`）三条约定：

1. **先校验、后动手**：非法 Zoom 先抛 `ValueError`，绝不留一个
   "配置没变、估算没了"的条目；
2. **值没变就什么都不做**（返回 `False`）：不许顺手把已经算好的估算清掉；
3. **值变了就作废估算**（`clear_estimate()`）并 `recalculate_totals()`：
   改 Zoom 就是换了一批瓦片，留着旧数字比留一个"尚未估算"更危险。

## 6. 不落盘的东西

- **等级不进 `plans.json`**。它由张数与容量现算，落盘等于多一份会过期的真值。
  计划的持久化字段仍是 Slice 20 的白名单。
- **面板上的风险结论与计划里的估算结果都不落盘**：打开时按当前配置重算 /
  复用已存的估算字段。

---

## 7. 界面约定

- **一律非模态**：`QMessageBox.show()` / `QDialog.show()` + `finished` 信号，
  **禁止 `exec()`**（会把 Qt 事件循环卡在那个框上，无头测试直接挂死）。
- **文案属于配置**：`app/config/settings.py` 里 `UI_TEXT_RISK_*` /
  `UI_TEXT_DANGEROUS_*` / `UI_TEXT_BUTTON_*` 是唯一来源，控件代码里不写句子。
- **确认词属于配置**：`DANGEROUS_CONFIRM_WORD`。
- **界面不出现机器码**：`RiskLevel.name` 只出现在 `label(with_value=True)`
  这种日志 / 验收文本里。

测试会继续"通过"，而它测的已经不是产品行为了。

## 9. 已知取舍

- **不预测下载耗时**：报告里有张数与容量，没有"大约要下多久" ——
  那个数字取决于当时的带宽、并发与限速，给一个会被现实打脸的估计不如不给。
- **不做配额核算**：天地图调用次数是按日限额的，但"今天还剩多少"只有服务端知道。
  强确认的那段话只说"会大量消耗配额"。
- **不自动缩小范围**：任何"帮你改小"的动作都必须由用户点（「采用推荐 Zoom」
  / 「停用危险项」），并且改完**不自动启动**。
- **阈值是常量，不是界面设置**：`RiskPolicy` 可注入（给将来的"保守 / 激进模式"
  留了口），但这一版没有把它做成界面上的选项 —— 一个能被随手调松的安全阈值
  等于没有阈值。
